### 3.2 finding 수정 플로우 (new policy 2026-05-21~)

1. **self-review 먼저** — `git diff <base>..HEAD` 직접 읽기. 8 영역 체크 ([feedback_review_flow.md](../../../.claude/projects/-Users-mj-IdeaProjects-study-note/memory/feedback_review_flow.md)):
   접근성 / 타입 가드 / 데이터 손실 / 영속화 실패 / 보안 / 회귀 / UX / caller propagation.
2. self-fix → commit → push.
3. `@codex review` 재트리거 (cross-review).
4. cross-finding 만 추가 fix.
5. PASS 되면 머지.

### 3.3 머지 순서

스택 구조이므로 **반드시 순서대로**:

1. PR #17 (S1) 머지 → 자동으로 PR #18 base 가 main 으로 변경.
2. PR #18 (S2) 머지 → PR #19 base 가 main 으로.
3. PR #19 (S3) 머지.

각 머지 후 `git fetch origin` 한 다음 다음 PR 의 자동 rebase / base 갱신 확인.

### 3.4 머지 후 배포

각 머지 후 운영 배포:
```bash
# 최신 FE 태그 확인
git tag -l 'fe-v*' --sort=-v:refname | head -3
# 다음 patch 버전 태그 push (예: fe-v0.1.12)
git tag fe-v0.1.X && git push origin fe-v0.1.X
```

Sprint-1 머지 묶음은 3 개를 합쳐서 single FE tag 로 한 번에 배포해도 OK (S1+S2+S3 가
같은 sprint 산출물이므로 release note 한 줄로 정리 가능).
